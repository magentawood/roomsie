## 2026-10-25 — T-05: Google sign-in works

- **What:** [#131](https://github.com/magentawood/roomsie/pull/131) adds Google sign-in on the web and `GET /v1/me` in the API. `jose` verifies the Firebase ID token with the cached keys of Google. The first sign-in makes the `users` row. A revoked token gets 401, and a user who is not active gets 403.
- **Why:** ADR-0007 makes the Bearer token the only auth mechanism. The grill added the status check, because a suspended user can get a new token.
- **Dead ends:**
  - With the default `now()`, the first token got 401 against its own new row. The row now starts `tokens_valid_after` at the `auth_time` of that token.
  - The first check compared `iat`. Firebase refreshes the token each hour with a new `iat`, so a revoked session came back. The check now compares `auth_time`, the time of the sign-in.
  - jose gives a plain `JOSEError` when Google's key server fails. A first version turned it into 401. The API now gives 401 only for token errors.
  - Port 8080 on the laptop had a different program, so the local API ran on 8081.
- **Next:** apply the migrations to the live database, so `/v1/me` works in production. Put the four `NEXT_PUBLIC_FIREBASE_*` values in Vercel. T-16a, T-17 and T-33 can start.

## 2026-10-25 — T-40: nightly backups of the two databases

- **What:** [#138](https://github.com/magentawood/roomsie/pull/138) adds `backup-databases.yml`. Each night it dumps the main and the analytics databases, restores each dump into a temporary Postgres 17, encrypts it with `age`, and keeps the newest fourteen in R2. A failure goes to the Telegram group.
- **Why:** the free plan of Supabase makes no backups ([PD13](../decisions/pd-13-databases-and-backups.md)).
- **Dead ends:**
  - A plain restore stops with "schema public already exists", because the dump makes the `public` schema. The restore check uses `--clean --if-exists`.
  - A scratch Supabase project for the restore test. The free plan allows two active projects, and the two databases use them. The done item now says "a scratch database".
  - A pipe from `age` into the upload. A `run` step does not stop on a failure inside a pipe, so a broken file could upload and the old dumps could go.
  - The R2 key of the API. Whoever leaks it could then delete the backups too. The workflow now has a key for the backups bucket only.
- **Next:** after the merge, add the two Telegram secrets and the two R2 backup secrets, run the workflow by hand, test the failure message, and do one restore on a laptop.


## 2026-10-26 — T-41: the listings API

The API signs photo upload links for R2 with `aws4fetch`, deletes photos in R2 before the rows, and masks phone numbers at save.
